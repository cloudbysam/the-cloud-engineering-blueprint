# Linux - Processes & Signals

## Processes
A process is any running application, shell command, or background task spawned by the kernel to perform work on the system (e.g., a web server, vulnerability scanner, web browser, or text editor). 

Each process has a unique **Process ID (PID)** used by the system to identify it. **PID 1** is always the **Init system** (`systemd` on most modern Linux distros), which is the very first user-space process started by the kernel. Except for PID 1, every process is created by a parent process, forming a hierarchical process tree.

## Signals
Signals are asynchronous notifications sent to processes to inform them of events or request actions. Signals can be sent by the kernel (e.g., when a process performs an illegal memory access), by parent processes, or manually by a user. 

The two most common termination signals are:
* **`SIGTERM` (15):** The default termination request. It asks a process to shut down gracefully, allowing it to save state and clean up resources.
* **`SIGKILL` (9):** An immediate, forced kill handled directly by the kernel. The process cannot catch, ignore, or clean up after this signal.

The **`kill`** command is used to send signals to running processes.

## Zombie Processes
A zombie process is a process that has completed execution but still has an entry in the process table because its parent process has not yet read its exit status (via the `wait()` system call). Zombies consume no memory or CPU resources, but they hold onto a process table slot until reaped.

## Systemd 
**Systemd** stands for *System Daemon*. In Linux, a daemon is a background process that runs continuously without direct user interaction. 

`systemd` is the primary init system in modern Linux distributions. As PID 1, it acts as the primary root ancestor for all other system and user processes.

## Unit Files
Creating a systemd **unit file** allows you to turn custom scripts or binaries into managed, automated background services. 

By defining a unit file, systemd manages service lifecycles, collects standard output/error logs, monitors resource limits, and automatically restarts services if they crash.

Custom, user-defined systemd service files are typically stored in:
`/etc/systemd/system/`

Service file names must end with the `.service` extension (e.g., `myscript.service`).

## Journalctl
When a systemd-managed service writes to standard output (`stdout`) or standard error (`stderr`) using commands like `echo` or `print()`, systemd automatically captures these log streams. To view and query these logs, use the **`journalctl`** utility.

## Useful Commands
* `ps aux` — View all running processes on the system with user details.
* `ps -ef --forest` — View process hierarchy in a visual tree format.
* `ps axjf` — Displays process tree details including standard PIDs and PPIDs.
* `top` — Real-time interactive process viewer.
* `htop` — Enhanced, interactive real-time process monitor.
* `man hier` — Description of the filesystem hierarchy.
* `kill -l` — List all available signal names and numbers.
* `kill -15 <PID>` or `kill <PID>` — Send `SIGTERM` to gracefully stop a process.
* `kill -9 <PID>` — Send `SIGKILL` to forcefully terminate a process.
* `lsof` — List all open files and the processes using them.
* `lsof -u <username>` — List open files owned by a specific user.
* `lsof -i :80` — Identify processes listening or communicating on port 80.
* `systemctl` — Control the systemd system and service manager.
* `journalctl` — Query and view logs generated by systemd services.
